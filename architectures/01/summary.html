ARCHITECTURE 01

Azure Bastion から閉域 PostgreSQL を管理する

Azure Portal から Bastion 経由で Jumpbox に入り、名前解決・5432・pgAdmin で閉域 PostgreSQL への接続を確かめる。

このテーマで学ぶこと

各項目には、それを自分の目で確かめる手順が紐づいている。

1

外部に出す入口は Bastion だけにし、Jumpbox には Public IP を付けない

Portal から VM を操作できることと、VM の管理ポートを公開することは別である。Bastion に Public IP を関連付け、Jumpbox の NIC をプライベート IP だけにすると、管理経路を一か所に絞れる。

→ 確認 1：Portal から Bastion 経由で Jumpbox に入る
2

Bastion と Jumpbox の NSG は、役割ごとに許可する通信が異なる

Bastion 側にはサービス運用に必要な受信規則があり、Jumpbox 側には Bastion サブネットからの RDP/SSH だけを通す規則がある。両者を同じ「踏み台用 NSG」としてまとめないことで、公開入口と VM の受信面を混同しない。

→ 確認 2：Portal で二つの NSG を比べる
3

閉域 DB の接続では、名前解決と TCP 5432 を分けて確認する

Jumpbox が DB の FQDN をプライベート IP に解決できても、5432 が通るとは限らない。PowerShell で二つを別々に観測すると、Private DNS と NSG のどちらを調べるべきか判断できる。

→ 確認 3：Jumpbox から DNS と 5432 を確認する
4

TCP 疎通だけで終わらせず、pgAdmin で認証と SQL 実行まで確認する

Test-NetConnection の成功はポートが開いていることしか証明しない。pgAdmin から testdb にログインしてクエリを実行すると、DB 資格情報、TLS、PostgreSQL サービスまで含めた接続を確認できる。

→ 確認 4：pgAdmin から DB に接続する

何を作ったか

Bastion を入口に、Windows Jumpbox を経由して VNet 統合した PostgreSQL を管理する Terraform 構成。

architecture.svg（クリックで拡大）
モジュール役割効いている設定
modules/network VNet、サブネット、Private DNS Zone と VNet リンクを作る。 PostgreSQL サブネットを Microsoft.DBforPostgreSQL/flexibleServers へ委任
modules/bastion Public IP を持つ Bastion と専用 NSG を作る。 sku = "Standard"、Static Standard Public IP
modules/jumpbox Public IP を持たない Windows 管理 VM と NSG を作る。 size = "Standard_B2ms"、Bastion 経由の RDP/SSH のみ受信
modules/database VNet 統合した PostgreSQL Flexible Server を作る。 public_network_access_enabled = false、32 GiB、7 日バックアップ

設計の要点

「そう書いてある」ではなく「そう書いた理由」。

管理の入口を Bastion に集める

Jumpbox の NIC に Public IP を定義せず、Bastion だけに Public IP を関連付ける。管理 VM の 3389 を直接公開する構成ではなく、Bastion のセッションを入口にする選択である。

DB の VNet 統合には DNS を含める

Flexible Server へ委任サブネットと Private DNS Zone を渡し、Zone を VNet にリンクする。Private access の接続は IP 到達性だけでは完結せず、DB の FQDN を VNet 内で解決できることまでが構成の一部になる。

Jumpbox のクライアント導入は手動にしている

VM 拡張でのツール導入はコメントアウトされている。Bastion 経由で RDP 接続した後、Jumpbox に pgAdmin 4 を手動で導入し、実際の管理経路をたどる構成である。

どう確認するか

Terraform の apply 完了後、手元のターミナルで接続情報を確認し、Azure Portal から実際の管理経路をたどる。VM と DB のパスワードは別物なので取り違えない。

手元で接続情報を確認する

この学習環境は root output を定義していないため、ローカル state から VM と DB の接続情報を確認する。表示したパスワードは記録や共有をせず、Bastion と pgAdmin の入力欄だけに使う。

terraform -chdir=main state show module.jumpbox.azurerm_windows_virtual_machine.jumpbox
terraform -chdir=main state show module.jumpbox.random_password.admin_password
terraform -chdir=main state show module.database.azurerm_postgresql_flexible_server.example
terraform -chdir=main state show module.database.random_password.db_password
確認 1

Azure Portal から Bastion 経由で Jumpbox に入る

ブラウザーだけで Windows Jumpbox へ RDP 接続し、VM に Public IP がなくても管理できることを確かめる。 ↑ 学び 1

手順
  1. Azure Portal で Jumpbox VM を開き、［接続］→［Bastion］を選ぶ。
  2. プロトコルは RDP、ポートは 3389、認証は［VM パスワード］を選ぶ。
  3. VM の管理者ユーザー名と VM 用パスワードを入力し、［接続］を押す。
  4. 新しいタブで Windows に入り、PowerShell で ipconfig を実行する。
期待される結果
  • ブラウザーの新しいタブに Windows デスクトップが表示される。
  • ipconfig の IPv4 アドレスが Jumpbox サブネットのプライベート IP になる。
  • VM の概要には Public IP が表示されない。
これでわかること
管理者は Bastion のブラウザーセッションを入口にできる。Jumpbox 自体の 3389 をインターネットへ公開しなくても、プライベート IP の VM を操作できる。
確認 2

Portal で二つの NSG の受信規則を比べる

Bastion のサービス用規則と、Jumpbox の VM 保護用規則を Azure Portal で見分ける。 ↑ 学び 2

手順
  1. Portal で対象リソースグループを開く。
  2. Bastion 用 NSG の［受信セキュリティ規則］を開く。
  3. 別タブで Jumpbox 用 NSG の［受信セキュリティ規則］を開く。
  4. 送信元、宛先ポート、優先度を見比べる。
期待される結果
  • Bastion NSG には HTTPS と Bastion サービス用の受信規則が表示される。
  • Jumpbox NSG には Bastion サブネットからの RDP/SSH 許可と、最後の全受信拒否が表示される。
これでわかること
Bastion の NSG はサービスが成立するための規則、Jumpbox の NSG は VM の受信面を絞るための規則である。同じ経路にあっても責務が異なる。
確認 3

Jumpbox から DNS と TCP 5432 を確認する

Bastion セッション内の PowerShell で、DB の名前解決とポート疎通を分けて確認する。 ↑ 学び 3

手順
$DbFqdn = "<Flexible Server の FQDN>"
Resolve-DnsName $DbFqdn
Test-NetConnection $DbFqdn -Port 5432 -InformationLevel Detailed
期待される結果
  • Resolve-DnsName が PostgreSQL サブネット内のプライベート IP を返す。
  • SourceAddress が Jumpbox のプライベート IP になる。
  • TcpTestSucceeded が True になる。
これでわかること
Private DNS Zone の VNet リンクが名前解決に使われ、Jumpbox から DB まで TCP 5432 が通る。DNS が失敗した場合と TCP だけ失敗した場合を分けて調べられる。
確認 4

Jumpbox の pgAdmin から DB に接続する

pgAdmin 4 を Jumpbox に導入し、DB 認証と SQL 実行まで成功することを確かめる。 ↑ 学び 4

手順
  1. Jumpbox の Edge で pgAdmin 4 の Windows 版公式ページを開き、最新の署名済みインストーラーを実行する。
  2. pgAdmin を起動し、［Register］→［Server］を開く。General の Name は任意の識別名にする。
  3. Connection に FQDN、5432、testdb、pgadmin、DB 用パスワードを入力し、Parameters の SSL mode を require にして保存する。
  4. testdb の Query Tool を開き、次の SQL を実行する。
SELECT current_database(), current_user,
       inet_server_addr(), inet_server_port(),
       version();
期待される結果
  • Object Explorer でサーバーと testdb を展開できる。
  • クエリ結果の database が testdb、user が pgadmin になる。
  • server address がプライベート IP、server port が 5432 になる。
これでわかること
Bastion から入った Jumpbox を DB クライアントとして使い、公開アクセスを有効にせず PostgreSQL へログインして SQL を実行できる。TCP 疎通だけでなく、DB サービスとして利用可能なことまで確認できる。

後始末とつまずき

後始末：課金を止める

Bastion、Windows VM、PostgreSQL Flexible Server は存在している間に課金される。学習を終えたら、同じ構成を使う予定がないことを確認してから削除する。

terraform -chdir=main destroy
az group exists --name "$RG_NAME"

AzureRM 5.x では DNS Zone の VNet リンクを ID で指定する

このテーマの provider は AzureRM 5.1.0 を使う。旧形式の resource_group_name と private_dns_zone_name は使えないため、現在のコードでは private_dns_zone_id を指定している。

Windows VM に DB クライアントは最初から入っていない

この Terraform は pgAdmin や psql をインストールしない。psql が認識されないのは導通障害ではないため、まず PowerShell で DNS/TCP を確認し、その後 pgAdmin を手動で導入する。

理解度チェック

設定を思い出せるかではなく、理由を自分の言葉で説明できるかを問う。チェック状態はこのブラウザに保存される。

  • Bastion に Public IP を置き、Jumpbox には置かない理由を説明できる。
  • Bastion と Jumpbox の NSG に別々の受信規則が必要な理由を説明できる。
  • 閉域 DB への接続確認で、名前解決と TCP 5432 を分ける理由を説明できる。
  • Test-NetConnection の成功と、pgAdmin で SQL を実行できることの違いを説明できる。
