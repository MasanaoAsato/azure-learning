ARCHITECTURE 01

Azure Bastion から閉域 PostgreSQL を管理する

Bastion を管理の入口に固定し、Jumpbox と VNet 統合した PostgreSQL の公開面を分けて確認する。

このテーマで学ぶこと

各項目には、それを自分の目で確かめる手順が紐づいている。

1

外部に出す入口は Bastion だけにし、Jumpbox には Public IP を付けない

Portal から VM を操作できることと、VM の管理ポートを公開することは別である。Bastion に Public IP を関連付け、Jumpbox の NIC をプライベート IP だけにすると、管理経路を一か所に絞れる。

→ 確認 1：Bastion と Jumpbox の IP 関連付けを比較する
2

Bastion と Jumpbox の NSG は、役割ごとに許可する通信が異なる

Bastion 側にはサービス運用に必要な受信規則があり、Jumpbox 側には Bastion サブネットからの RDP/SSH だけを通す規則がある。両者を同じ「踏み台用 NSG」としてまとめないことで、公開入口と VM の受信面を混同しない。

→ 確認 2：二つの NSG の受信規則を比べる
3

PostgreSQL を VNet 統合すると、公開アクセスを無効にしても VNet 内から接続できる

Flexible Server には委任サブネットと Private DNS Zone を渡し、`public_network_access_enabled = false` を指定している。接続可否は「インターネットから到達できるか」ではなく、委任されたサブネットと DNS を含む VNet 内の経路で決まる。

→ 確認 3：DB のネットワーク設定を取得する
4

閉域 DB の接続では、ポートだけでなく Private DNS Zone の VNet リンクも確認する

Jumpbox が DB の FQDN を解決できなければ、5432 の許可規則だけでは接続できない。DNS Zone を VNet にリンクし、DB 用の A レコードが作成されるところまで見ると、名前解決とネットワーク到達性を分けて説明できる。

→ 確認 4：DNS Zone の VNet リンクとレコードを見る

何を作ったか

Bastion を入口に、Windows Jumpbox を経由して VNet 統合した PostgreSQL を管理する Terraform 構成。

architecture.svg（クリックで拡大）
モジュール役割効いている設定
modules/network VNet、サブネット、Private DNS Zone と VNet リンクを作る。 PostgreSQL サブネットを Microsoft.DBforPostgreSQL/flexibleServers へ委任
modules/bastion Public IP を持つ Bastion と専用 NSG を作る。 sku = "Standard"、Static Standard Public IP
modules/jumpbox Public IP を持たない Windows 管理 VM と NSG を作る。 size = "Standard_B2ms"、Bastion 経由の RDP/SSH のみ受信
modules/database VNet 統合した PostgreSQL Flexible Server を作る。 public_network_access_enabled = false、32 GiB、7 日バックアップ

設計の要点

「そう書いてある」ではなく「そう書いた理由」。

管理の入口を Bastion に集める

Jumpbox の NIC に Public IP を定義せず、Bastion だけに Public IP を関連付ける。管理 VM の 3389 を直接公開する構成ではなく、Bastion のセッションを入口にする選択である。

DB の VNet 統合には DNS を含める

Flexible Server へ委任サブネットと Private DNS Zone を渡し、Zone を VNet にリンクする。Private access の接続は IP 到達性だけでは完結せず、DB の FQDN を VNet 内で解決できることまでが構成の一部になる。

Jumpbox のクライアント導入は手動にしている

VM 拡張でのツール導入はコメントアウトされており、Bastion 経由で RDP 接続した後に DB クライアントを手動で入れる前提である。自動構成までをこのテーマの完了条件には含めない割り切りになっている。

どう確認するか

実リソース名は環境ごとに異なるため、プレースホルダを置き換えて Azure CLI で確認する。Azure CLI へのサインインと、Terraform の apply 完了が前提。

共通の準備

az login
export RG_NAME='<resource-group-name>'
export BASTION_NAME='<bastion-name>'
export VM_NAME='<jumpbox-vm-name>'
export PG_NAME='<postgres-server-name>'
確認 1

Bastion と Jumpbox の IP 関連付けを比較する

Bastion には Public IP があり、Jumpbox の NIC には Public IP がないことを確かめる。 ↑ 学び 1

手順
BASTION_PIP_ID=$(az network bastion show -g "$RG_NAME" -n "$BASTION_NAME" --query 'ipConfigurations[0].publicIPAddress.id' -o tsv)
NIC_ID=$(az vm show -g "$RG_NAME" -n "$VM_NAME" --query 'networkProfile.networkInterfaces[0].id' -o tsv)
az network public-ip show --ids "$BASTION_PIP_ID" --query '{sku:sku.name,allocation:publicIPAllocationMethod}' -o json
az network nic show --ids "$NIC_ID" --query '{private:ipConfigurations[0].privateIPAddress,public:ipConfigurations[0].publicIPAddress.id}' -o json
期待される結果
  • Bastion の Public IP は Standard SKU、Static 割り当てとして表示される。
  • Jumpbox の NIC は private のみが表示され、public は null または空になる。
これでわかること
Portal からの管理アクセスは Bastion の Public IP を通る。Jumpbox 自体にインターネットから接続する経路を作っていないことを、二つのリソースの差として確認できる。
確認 2

二つの NSG の受信規則を比べる

Bastion のサービス用規則と、Jumpbox の VM 保護用規則を見分ける。 ↑ 学び 2

手順
BASTION_NSG=$(az network nsg list -g "$RG_NAME" --query "[?contains(name, 'bastion')].name | [0]" -o tsv)
JUMPBOX_NSG=$(az network nsg list -g "$RG_NAME" --query "[?contains(name, 'jumpbox')].name | [0]" -o tsv)
az network nsg rule list -g "$RG_NAME" --nsg-name "$BASTION_NSG" --query "[?direction=='Inbound'].{name:name,port:destinationPortRange,source:sourceAddressPrefix}" -o table
az network nsg rule list -g "$RG_NAME" --nsg-name "$JUMPBOX_NSG" --query "[?direction=='Inbound'].{name:name,access:access,port:destinationPortRange,source:sourceAddressPrefix}" -o table
期待される結果
  • Bastion NSG には HTTPS と Bastion サービス用の受信規則が表示される。
  • Jumpbox NSG には Bastion サブネットからの RDP/SSH 許可と、最後の全受信拒否が表示される。
これでわかること
Bastion の NSG はサービスが成立するための規則、Jumpbox の NSG は VM の受信面を絞るための規則である。同じ経路にあっても責務が異なる。
確認 3

DB のネットワーク設定を取得する

Flexible Server の public access、委任サブネット、Private DNS Zone を一度に確認する。 ↑ 学び 3

手順
az postgres flexible-server show -g "$RG_NAME" -n "$PG_NAME" \
  --query '{public:network.publicNetworkAccess,delegatedSubnet:network.delegatedSubnetResourceId,privateDnsZone:network.privateDnsZoneArmResourceId}' \
  -o json
期待される結果
  • public は Disabled と表示される。
  • delegatedSubnet と privateDnsZone のリソース ID が空でない。
これでわかること
この DB は Public access の IP 許可リストで守るのではなく、VNet に注入する Private access で配置されている。DB の接続先を VNet 内のクライアントに限定する設計だと確認できる。
確認 4

DNS Zone の VNet リンクとレコードを見る

Private DNS Zone が VNet と結び付けられ、DB の名前解決に使う A レコードがあることを確かめる。 ↑ 学び 4

手順
DNS_ZONE_ID=$(az postgres flexible-server show -g "$RG_NAME" -n "$PG_NAME" --query 'network.privateDnsZoneArmResourceId' -o tsv)
DNS_ZONE_NAME=${DNS_ZONE_ID##*/}
az network private-dns link vnet list -g "$RG_NAME" -z "$DNS_ZONE_NAME" --query '[].{name:name,vnet:virtualNetwork.id,registration:registrationEnabled}' -o table
az network private-dns record-set a list -g "$RG_NAME" -z "$DNS_ZONE_NAME" --query '[].{name:name,records:arecords[].ipv4Address}' -o table
期待される結果
  • VNet link が 1 件以上表示され、VNet のリソース ID を指す。
  • DB に対応する A レコードが表示される。
これでわかること
DB の Private DNS Zone を VNet にリンクすることで、同じ VNet の Jumpbox から FQDN をプライベート アドレスへ解決できる。接続障害時には、5432 と DNS を別の観点で切り分けられる。

後始末とつまずき

後始末：課金を止める

Bastion、Windows VM、PostgreSQL Flexible Server は存在している間に課金される。学習を終えたら、同じ構成を使う予定がないことを確認してから削除する。

terraform -chdir=main destroy
az group exists --name "$RG_NAME"

AzureRM 5.x では DNS Zone の VNet リンクを ID で指定する

このテーマの provider は AzureRM 5.1.0 を使う。旧形式の resource_group_name と private_dns_zone_name は使えないため、現在のコードでは private_dns_zone_id を指定している。

apply 前にサブスクリプションのプレースホルダを置き換える

root module の provider 設定ではサブスクリプション ID がプレースホルダになっている。実 ID をコードへ固定せず、認証方法に合わせて安全に設定してから plan/apply する。

理解度チェック

設定を思い出せるかではなく、理由を自分の言葉で説明できるかを問う。チェック状態はこのブラウザに保存される。

  • Bastion に Public IP を置き、Jumpbox には置かない理由を説明できる。
  • Bastion と Jumpbox の NSG に別々の受信規則が必要な理由を説明できる。
  • VNet 統合した PostgreSQL が Public access とどう異なるかを説明できる。
  • 閉域 DB への接続確認で、ポート確認と DNS 確認を分ける理由を説明できる。
